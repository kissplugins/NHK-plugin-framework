🔧 State/Lifecycle Patterns in WordPress You Can Combine With FSMs

These aren’t FSMs by themselves, but they’re great foundations and hooks around which to design one.

Gutenberg Data Stores

The Block Editor uses Redux-like state via @wordpress/data. Useful for UI state; pair with an explicit FSM for flows.

Use for: Complex block interactions, editor states

REST API Lifecycle Hooks

Interception points like rest_pre_dispatch, rest_dispatch_request, rest_post_dispatch.

Use for: Guarding/triggering transitions around requests

Post Status Transitions

Built-in hooks: transition_post_status, {old_status}_to_{new_status}

Use for: Editorial workflow management

Comment Moderation States

Status flow via wp_set_comment_status

Use for: UGC moderation

Cron & Background Jobs

WP-Cron (wp_schedule_event, wp_schedule_single_event) + your own job tables.

Use for: Retries, time-based transitions

Customizer & Live Preview

Preview lifecycle (customize_preview_init) with staged → committed changes.

Use for: Draft/apply/commit style flows

Storage & Auditing

Keep a single source of truth for state, plus an immutable transition log.

Use for: Support, analytics, compliance

⚠️ Race Conditions & Retries

Admin clicks + webhooks + cron can fire the same transition concurrently. Use locking (row-level lock or version column) and idempotent side effects. Implement retryable vs permanent failure states with exponential backoff.

❌ When to AVOID FSMs in WordPress

IndicatorDescriptionBetter Alternative
Simple Binary StatesOnly on/off or true/false statesupdate_option() or update_post_meta()
Stateless OperationsActions that don't depend on previous stateUse action/filter hooks directly
One-time ActionsFire-and-forget operationswp_schedule_single_event()
Read-only DisplayShowing data without state changesWP_Query and template functions
Truly Tiny FeatureSingle-purpose where state adds no clarityKeep procedural & simple
Anti-patterns:
  • State implied by many flags (is_paid, is_shipped, is_refunded) — contradictions ensue. Prefer one state column.
  • Hidden transitions inside random hooks — route all changes through a single transition function.
  • “Just a few if/else checks” that grow unbounded — formalize as an FSM early.

🧩 Minimal Implementation Patterns

PHP (backend FSM core)

// PHP 8.1+
enum OrderState: string { case Draft='draft'; case Pending='pending'; case Processing='processing'; case Completed='completed'; case Failed='failed'; }

final class OrderFsm {
  public function __construct(private wpdb $db) {}

  public function transition(int $orderId, OrderState $from, OrderState $to, array $ctx=[]): void {
    // example guard
    if ($from === OrderState::Pending && $to === OrderState::Processing && empty($ctx['payment_valid'])) {
      throw new RuntimeException('Payment not validated');
    }
    $this->db->query('START TRANSACTION');
    $row = $this->db->get_row($this->db->prepare(
      "SELECT state, version FROM wp_orders WHERE id=%d FOR UPDATE", $orderId
    ));
    if ($row->state !== $from->value) { throw new RuntimeException('Stale state'); }

    do_action('myplugin_fsm_before_transition', $orderId, $from, $to, $ctx);

    $this->db->update('wp_orders',
      ['state' => $to->value, 'version' => $row->version + 1, 'updated_at' => current_time('mysql', true)],
      ['id' => $orderId]
    );

    $this->db->query('COMMIT');
    // do side effects after commit
    do_action('myplugin_fsm_after_transition', $orderId, $from, $to, $ctx);
  }
}

Editor/Admin (React) with a true FSM

// xstate pairs nicely with Gutenberg components
import { createMachine } from 'xstate';

export const uploadMachine = createMachine({
  id: 'upload',
  initial: 'idle',
  states: {
    idle: { on: { START: 'uploading' } },
    uploading: { on: { PROGRESS: 'uploading', SUCCESS: 'processing', FAILURE: 'retrying' } },
    processing: { on: { SUCCESS: 'done', FAILURE: 'retrying' } },
    retrying: { on: { RETRY: 'uploading', ABORT: 'failed' } },
    done: { type: 'final' },
    failed: { type: 'final' }
  }
});

💡 Real-World WordPress Plugin Examples

✅ Good FSM Use: Booking plugin with states: available → reserved → confirmed → completed → cancelled. Each transition sends emails, updates calendars, and processes payments.
❌ Overkill FSM: A simple contact form that just sends an email. Better to use basic validation and wp_mail().
✅ Good FSM Use: Migration plugin with states: idle → scanning → migrating → verifying → complete, with progress tracking and rollback.
⚠️ Maybe FSM: Cache management plugin. Simple invalidation doesn't need FSM, but if you add warming, partial rebuilds, and staged deployment, FSM helps.
