🔧 WordPress Core FSM Patterns You Can Reuse

Gutenberg Data Stores

The Block Editor uses Redux-like state management with @wordpress/data

Use for: Complex block interactions, editor states

REST API Controller States

WordPress REST API handles request states: rest_pre_dispatch, rest_dispatch

Use for: API endpoint state management

Post Status Transitions

Built-in hooks: transition_post_status, {old_status}_to_{new_status}

Use for: Content workflow management

Comment Moderation States

Comment status flow: wp_set_comment_status

Use for: User-generated content moderation

Cron Job States

WP-Cron scheduling: wp_schedule_event with state tracking

Use for: Background task management

Customizer States

Theme Customizer: customize_preview_init state handling

Use for: Live preview functionality

✅ When to USE FSMs in WordPress

Indicator Description WP Example
Multiple Valid States Your feature has 3+ distinct states with specific behaviors Post status: draft → pending → published → archived
Complex Transitions State changes have conditions, validations, or side effects WooCommerce order: pending → processing (payment validated) → completed
Async Operations Managing loading, success, error, and retry states Media upload with progress tracking
User Journey Tracking Need to know where users are in a process Membership registration flow
Rollback Requirements Need to revert to previous states safely Form autosave and recovery

❌ When to AVOID FSMs in WordPress

Indicator Description Better Alternative
Simple Binary States Only on/off or true/false states Use update_option() or update_post_meta()
Stateless Operations Actions that don't depend on previous state Use action/filter hooks directly
One-time Actions Fire-and-forget operations Use wp_schedule_single_event()
Read-only Display Showing data without state changes Use WP_Query and template functions
Small Plugins Under 500 lines of code, single purpose Keep it simple with procedural code

💡 Real-World WordPress Plugin Examples

✅ Good FSM Use: A booking plugin with states: available → reserved → confirmed → completed → cancelled. Each transition sends emails, updates calendars, and processes payments.
❌ Overkill FSM: A simple contact form that just sends an email. Better to use basic validation and wp_mail().
✅ Good FSM Use: Migration plugin with states: idle → scanning → migrating → verifying → complete, with progress tracking and rollback capability.
⚠️ Maybe FSM: Cache management plugin. Simple invalidation doesn't need FSM, but if you have warming states, partial rebuilds, and staged deployment, FSM helps.

🚀 Quick Decision Framework

Ask Yourself:

Can I draw a state diagram with 3+ states? → Consider FSM
Are transitions conditional or complex? → Use FSM
Do I need to track history or allow rollback? → Use FSM
Is it just CRUD with hooks? → Skip FSM
Am I managing async workflows? → Use FSM
